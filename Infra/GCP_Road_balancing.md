# 요청이 Cloud Run 컨테이너에 닿기까지 

1. DNS 레코드
브라우저가 portal.aify.ai 를 IP 로 변경 → 이 IP 가 부하 분산기의 전역 애니캐스트 주소 : 트래픽이 어느 LB 로 갈지 결정


2. 전달 규칙 Forwarding Rule
IP + 프로토콜 + 포트의 조합 
결정 : 포트 80 과 443을 각각을 받을지 말지 -> 포트마다 별개 규칙이 필요하다. 


3. 타겟 프록시 (Target Proxy)

요청을 받아 해석하는 주체
HTTP용 (target-http-proxy) 과 HTTPS 용 (target-https-proxy)이 서로 다른 리소스 
결정 : TLS 를 여기서 종료(termination) 할지 , 평문으로 받을지 

4. SSL 인증서
HTTPS 프록시에만 붙는다. Google 관리형 또는 직접 업로드
어느 도메인 이름으로 HTTPS를 제공할지 여기 없는 도메인은 인증서 오류가 난다. 

* https:// 로 온 요청은 내용이 암호화돼 있습니다. 부하 분산기가 SSL 인증서를 써서 그걸 풀어야 어느 경로로 보낼지 판단할 수 있습니다. 그 복호화 작업이 HTTPS 프록시의 역할입니다.


5. URL 맵, URL Map 
호스트 이름과 경로를 보고 어디로 보낼지 정한다. 
백엔드로 넘기거나, 백엔드 없이 리다이렉트 응답을 직접 반환하거나 
HTTP -> HTTPS 리다이렉트가 후자 


6. 백엔드 서비스 
운영 설정이 전부 여기 모인다. 타임아웃(기본 30초), 액세스 로그, Cloud CDN, Cloud Armor
결정하는 것 : 얼마나 기다릴지, 무엇을 기록할지 


7. 서버리스 NEG, Network Endpoint Group 
백엔드 서비스와 Clopud Run 서비스를 잇는 연결 고리
Cloud Run 은 VM 이 아니라서 인스턴스 그룹이 아닌 서버리스 NEG 를 쓴다. 
결정 : 어느 Cloud RUn 서비스로 보낼지 


8. Cloud Run 서비스
aify-portal-frontend 컨테이너가 요청을 받아 Next.js SSR 을 실행한다. 여기서부터가 Cloud RUn 로그의 영역 (Cloud Run 로그에는 8번에 도달한 요청만 남는다. 1~7번에서 막이면 서버로그에는 아무 흔적도 없다.)\




# HTTP, HTTPS 

하나의 LB 가 80과 443 을 같이 처리하는게 아니라, 포트마다 전달 규칙 -> 프록시 -> URL 맵이 각각 따로 존재
콘솔에 부하 분산기가 두개 
DNS 는 IP 하나만 가리키므로, 그 IP 에 80과 443 규칙이 모두 붙어 있어야 양쪽이 동작한다. 
리다이렉트 전용 LB 에는 액세스 로그가 없습니다. 로그는 백엔드 서비스 기능인데, 리다이렉트 URL 맵에는 백엔드 서비스가 없습니다. HTTP 쪽 요청은 기록할 방법이 없습니다. 



# 발생 문제 : 초기 

한번도 저희 사이트를 방문하지 않은 사람이 주소창에 portal.aify.ai 만 입력하면 Chrome은 스킴을 모릅니다.
1. 히스토리/사이트 데이터 삭제 (반복 테스트했습니다) → "이 사이트는 HTTPS" 기록이 사라짐
   ↓
2. portal.aify.ai 입력 → Chrome이 http:// (포트 80)로 접근
   ↓
3. HTTP 경로에서 응답을 받지 못해 대기 → ERR_TIMED_OUT 🔴
   포트 80 자체는 301로 https 주소를 안내하며 정상 응답합니다
   HTTP 경로의 어느 단계에서 멈추는지는 특정하지 못했습니다
   찬희 팀장님이 말하신 한번도 사이트에 방문하지 않은 유저로 로그인한 후 접근시 발생의 이유

↓
4. 잠시 후 재시도가 일어나 HTTPS로 정상 로드(저는 알아서됨) ✅
   ↓
5. Chrome이 "이 도메인은 HTTPS"를 기록 → 두 번 다시 안 뜸
   https://portal.aify.ai/ 로 입력하면 2번 오류가 없습니다. 그래서 히스토리를 몇 번이고 지우고 재시도해도 에러가 나지 않았습니다. 


# 해결방법 : http -> https 로 리다이렉트 


1. 80 과 443이 같은 IP 에 붙어있는지가 핵심 

참고 : 실패한 요청은 LB 의 액세스 로그를 켜면 확인이 가능하다.
한계 : 로그는 HTTPS 쪽(백엔드가 있는 사슬)만 기록됩니다. 리다이렉트 전용 LB는 백엔드 서비스가 없어서 켤 수 없습니다. HTTP 진입 자체를 관찰하려면 여전히 브라우저의 chrome://net-export 가 필요합니다.



# GFE 
Cloud Run 은 앞단에 Google Front End(GEF)가 있어서, *.run.app 주소만으로도 인스턴스 간 요청 분산과 오토스케일링을 자동으로 한다. 그것은 Cloud Load Balancing 제품은 아니다. 


# 커스텀 도메인 
커스텀 도메인을 붙이는 방법은 2가지가 있다.
1) Cloud Run 도메인 매핑 : 간단하지만 LB 리소스가 없어서 위 기능들을 못 쓴다.
2) Global External Application LB + 서버리스 NEG : 직접 구축해야 하지만 전부 사용 가능 




                      Cloud Run 기본(*.run.app)       LB 구성 (portal.aify.ai) 
요청 분산 · 오토스케일링 : 	✅ GFE가 자동	✅
콘솔 "부하 분산" 메뉴에 표시 : 	❌	✅
전달 규칙 · URL 맵 · 백엔드 서비스 리소스 : 	❌ 없음	✅ 있음

# 부하분산기

전달규칙 : 이 포트로 온 요청을 받을지 말지 (80 이냐 443 이냐)
  
라우팅과 분산은 구분해야함. 



# 우리 서비스 예시 
portal.aify.ai
│ DNS
▼
공인 IP (애니캐스트)
│
├── 포트 80  → 부하 분산기 "portal-http-redirect"
│              → URL 맵이 301 리다이렉트 응답만 반환 (백엔드 없음)
│
└── 포트 443 → 부하 분산기 "portal-urlmap"
→ URL 맵 → 백엔드 서비스 → NEG → Cloud Run

# 부하 분산기 구성 방식 두가지
1) 부하 분산기 1개에 프런트엔드 2개 (IP:80   → HTTP, IP:443  → HTTPS)
2) 부하 분산기 2개로 분리
   부하 분산기 "portal-http-redirect"  →  IP:80
   부하 분산기 "portal-urlmap"         →  IP:443

# 부하 분산기 후 
부하 분산기 뒤로는 평문으로 갑니다. Google 내부망이라 안전하지만, 컨테이너 입장에서 보면 모든 요청이 HTTP로 보입니다.

브라우저가 https:// 로 접속
↓
Cloud Run 컨테이너가 실제로 받는 것:  http://  (평문)
원본 스킴은 헤더로 전달:  X-Forwarded-Proto: https


그래서 앱 코드에 "HTTP면 HTTPS로 리다이렉트"를 넣으면 안 됩니다. 모든 요청이 http로 보이니 무한 리다이렉트 루프가 납니다. 아주 흔한 함정입니다.
앞서 "앱에서 HTTP→HTTPS 리다이렉트 코드는 효과 없다"고 한 이유가 두 가지였던 겁니다:
포트 80 요청은 애초에 portal-http-redirect가 301로 처리해서 컨테이너까지 오지 않습니다
포트 443으로 온 요청은 컨테이너에 평문으로 도착하므로, 스킴만 보고 판단하면 정상 요청까지 리다이렉트해버립니다
SSL 인증서는 부하 분산기에만 있으면 됩니다. Cloud Run 컨테이너에는 인증서를 넣을 필요가 없습니다
인증서 갱신도 부하 분산기 쪽 일입니다 (Google 관리형이면 자동)
Cloud Run 컨테이너에는 인증서가 필요 없습니다. 앞서 설명한 TLS 종료 때문입니다. 암호화 구간이 부하 분산기에서 끝나므로 인증서도 거기에만 있으면 됩니다.


# Cloud CDN : 응답을 엣지에 캐시 

전 세계 Google 엣지에 응답을 저장해두고, 다음 요청은 백엔드까지 가지 않고 가까운 엣지에서 바로 돌려준다.
[CDN 없음]  브라우저 → 엣지 → 서울 리전 Cloud Run → 응답        (매번)

[CDN 있음]  브라우저 → 엣지 (캐시에 있음) → 응답                 (2번째부터)

캐시 여부는 응답 헤더로 판단합니다. Cache-Control을 보고 캐시 가능한 것만 저장합니다.

# Cloud Armor : 엣지에서 차단하는 방화벽 

WAF(웹 애플리케이션 방화벽) + DDos 방어 -> 요청이 백엔드에 닿기 전에 엣지에서 차단
규칙	용도
IP · 지역 차단	특정 국가/IP 대역 거부
사전 정의 규칙	SQL 인젝션 · XSS 패턴 자동 차단
속도 제한	초당 N회 넘으면 거부
Host 헤더 검사	도메인이 아닌 요청 거부
봇 관리	자동화 트래픽 식별



# NEG : Network Endpoint Group 백엔드 목록 

부하 분산기가 트래픽을 보낼 대상 목록 
부하 분산기의 백엔드는 VM 그룹 (인스턴스 그룹) 구체적인 IP 포트 목록 -> Cloud Run 에는 그런게 없음
인스턴스가 뜨고 내려가고, IP 도 계속 바뀐다. 
가리킬 고정 주소가 없어서 GCP 가 더 일반화된 단위를 반든게 NEG 다
IP도 포트도 없습니다. 그냥 "이 리전의 이 Cloud Run 서비스" 라는 이름표입니다.

즉 NEG는 어댑터 역할입니다 — 부하 분산기 쪽은 "엔드포인트 그룹"을 기대하고, Cloud Run 쪽은 이름으로 식별되는 관리형 서비스인데, 그 둘을 이어주는 것
